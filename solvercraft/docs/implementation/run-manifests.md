# Typed diagnostic run manifests

The reusable `solvercraft::run_manifest` API prepares a bounded fingerprint before execution and attaches a typed manifest to an object result afterwards. CLI results keep their original top-level fields; the additional field is `manifest`. Modern `execute` and legacy `solve` keep their existing workflow/provenance layouts; legacy solve also gains additive engine, entrypoint, snapshot and result-locator fields.

`prepare(entrypoint, &request, configuration, max_bytes)` returns `PreparedManifest<C>`. Its configuration may borrow options directly from the request. `complete(&result, actual_engine, result_location)` returns a serializable `Run` that borrows the result. Neither operation converts the request/result to `serde_json::Value`, clones a result matrix, nor serializes it into an intermediate byte buffer. Object results passed to this wrapper must not already have a `manifest` field.

`diagnostic_fingerprint` streams compact Serde JSON into FNV-1a64 with a checked byte count and a hard ceiling of 16 MiB; callers can choose a smaller ceiling. The typed request includes expanded defaults and original input/model data. If that normalized stream exceeds its limit, the request fails before the numerical calculation begins. The CLI also independently rejects raw input larger than 16 MiB. The encoding is versioned, diagnostic and noncryptographic. It is deterministic for the same typed serializer stream, but it does not assert canonical map ordering across different input types or protect against intentional collisions.

Output expression trees and information-value payoff matrices are input/model data identified by the complete request fingerprint; manifests record output counts or information dimensions and all utility/acquisition settings instead of duplicating those trees/matrices on a rejected request. The fixed `demo` also records its real LP options and simulation options (10,000 trials, seed42), keeping both original result keys.

Each new manifest records the SDK version, command entrypoint, native/WASM target OS/architecture/family/pointer width, input fingerprint and byte count, typed effective configuration, actual engine/algorithm and result locator. Defaults are visible, including budgets, tolerances and exact decimal-string `u64` seeds. A default snapshot is explicitly tagged `diagnostic_request_fingerprint`; it never invents a workbook revision, hostname or verified source-build identity. Embedded hosts can supply an explicitly labelled `caller_supplied` snapshot ID/revision through `with_caller_snapshot`. Solvercraft does not attest the truth of those caller values.

| --- | --- |

| `chance`, `finite` | Chance rule or full finite-constraint specification |
| `multiobjective` | Goals, weights/priorities/epsilon bounds and tolerances |
| `robust-box`, `robust-budget`, `robust-ellipsoid` | Uncertainty sets and reformulation options |
| `decision-tree`, `information-value` | Memory limit and utility/information configuration |
| `solve-sparse`, `solve-conic`, `solve-mixed-conic`, `solve-discrete`, `solve-global`, `recourse`, `benders` | Full effective solve options; model/problem data remain identified by the input fingerprint |

Direct numerical solve manifests copy the returned engine identifier, including actual Clarabel routing rather than the requested `auto` method. Aggregate algorithms identify their executed wrapper algorithm; per-stage backend/fit/sampling identities remain in the existing stage/fit/run result fields. For multistart, the returned solution's engine is retained. Result locations use the CLI's `stdout:$` or `stdout:$.result`; other hosts supply their own locator.

Prepared CLI scopes also retain identity on failure. Errors after preparation are streamed as one stderr object with the existing `code` and `message` plus an additive manifest. The request/configuration remains borrowed while the error is written; no JSON value tree or input matrix is cloned. A process-local reporting marker prevents the outer entrypoint from appending a second error document. If no typed result is admitted, the actual engine is explicitly `unknown` and the locator is `stderr:$`. Raw input/strict deserialization and fingerprint-preparation errors keep the original bare error format. Numerical errors before result output leave stdout empty; an external I/O failure while streaming output can inherently interrupt that output.

Executed evidence on Rust 1.95 / Windows: `crates/solvercraft/tests/run_manifest.rs` has three controls for bounded streaming, borrowing without Clone bounds, snapshot identity and metadata limits. `crates/cli/tests/manifests.rs` has thirteen real-process suites for conic backend identity, high seeds/repetition/input changes, advanced Sobol/copula/invalid-trial configuration, fit/grid settings, nonlinear/multistart/compiled-expression settings, risk/SAA seeds, the remaining discrete/decision/multiobjective/robust routes, the fixed LP/10,000-trial demo nine admitted-error routes with strict decode controls, original-domain robust support/formation precision controls, and exact binary-branch/large-offset/interruption controls. Independent `api_review` reproduces a finite admitted information-value problem whose calculation overflows and verifies the retained error trace. Existing advanced process fixtures separately check additive manifest coverage on their successful workflows; together the positive fixtures cover all 23 non-execute advanced commands. Full platform and host-job acceptance must cite their own executed gates; these CLI tests do not establish every host integration.
